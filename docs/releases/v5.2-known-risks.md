# Known Risks: ABST-GP V5.2 Document Intelligence Pipeline

Este documento enumera los riesgos operativos y técnicos aceptados o descubiertos durante la estabilización y preparación para la migración V2.

## Operación Síncrona de Cotización y Comparación
El endpoint `POST /comparison/run` bloquea la fila del expediente de manera pesimista (`FOR UPDATE`) y ejecuta el motor OCR/Comparación dentro del ciclo de request HTTP síncrono.
- **Riesgo:** Si el motor demora más que el `lock_timeout` de PostgreSQL o el timeout de Axios, la conexión puede caer dejando la base de datos bloqueada para otros procesos.
- **Mitigación Futura:** Trasladar la ejecución del motor a una tarea Celery / Background Worker asíncrona, de forma similar al procesamiento del documento de requerimiento.

## Memoria del Blob PDF y Visor Nativo
El documento PDF se entrega al frontend mediante un `Blob` instanciado a través de `URL.createObjectURL()`.
- **Riesgo:** Consumo elevado de memoria del navegador si los PDFs son excesivamente grandes o si el usuario abre múltiples expedientes en la misma sesión sin que el GC actúe rápidamente (aunque se haya implementado `revokeObjectURL`).
- **Riesgo:** Dependencia del visor PDF nativo del navegador, que no expone APIs de búsqueda programática para resaltar evidencias automáticamente en V2.
- **Mitigación Futura:** Evaluar `pdf.js` si V2 requiere marcadores visuales sincronizados.

## Ausencia de Confianza (Confidence) y Evidencia
El motor V1 (`comparison_engine.py`) no provee coordenadas, número de página ni score probabilístico de confianza en los DTOs actuales.
- **Riesgo:** El Frontend UI ya tiene la estructura adaptada, pero los valores se mantienen ocultos / ignorados al ser `null`.
- **Mitigación:** Ninguna, el modelo de datos de V1 carece de esta semántica. Será solucionado por diseño en V2.

## Transaccionalidad Incompleta del Registro de Auditoría (AuditLog)
La auditoría operativa no es disparada en la misma transacción SQLAlchemy o no se rastreó su acoplamiento en `cases.py` para la comparación.
- **Riesgo:** Si ocurre una desconexión entre el guardado principal y el log, podrían existir casos donde no quede rastro auditable de la ejecución de la comparación, a pesar de que el estado cambió exitosamente a `READY_GENERATE`.
- **Mitigación Futura:** Integrar `AuditLog` dentro de los bloques `try-except` atados a la misma sesión SQLAlchemy y hacer trigger previo al `db.commit()`.

## V1 versus V2: Estrategia Ring 2
La UI fue refactorizada a tipos agnósticos (`ConditionComparison`), garantizando que cuando el Backend habilite V2 no rompa la aplicación cliente. 
- **Riesgo:** Un esquema dual V1/V2 en Backend sin migración de datos histórica podría producir discrepancias en el comportamiento del OutputGenerator.
- **Mitigación:** Asegurar un "Rollback Operacional" donde la bandera V2 pueda deshabilitarse de inmediato regresando al motor puro V1 estabilizado aquí sin modificar la base de datos existente.

## Conclusión
La arquitectura actual implementada en V5.2 protege la integridad transaccional de PostgreSQL, asegurando que **nunca existan filas duplicadas** gracias al Lock explícito. Sin embargo, **la alta acoplación HTTP-Síncrona restringe su escalabilidad** para expedientes gigantes. La actualización asíncrona de V2 será crítica.
